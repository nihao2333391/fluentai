# Fluent AI｜02-D Agent 能力仓库、知识检索与工具注册

**所属模块：02 工程辅助 Agent 与能力库**

**版本：V0.1**

**状态：初步需求规格，待业务确认与技术整合**

## 一、模块定位

本模块负责管理工程辅助 Agent 可以使用的专业能力。

能力按照零件目录组织。同一目录下的多个模板 Agent 可以共享该目录的专业知识、工程规则、Prompt 和已授权工具。

每个模板 Agent 保持独立的身份、会话及运行状态。

### 1.1 核心架构

每个零件目录对应一个共享能力空间。

该空间由两类主要资源库组成：

1. **专业知识与规则库**：保存工程文档、经验规则及 Prompt。
2. **工具库**：保存已经注册的计算工具及其接口定义。

Agent Runtime 根据当前模板所属目录，加载对应的有效能力。

### 1.2 能力分类与职责

| 能力类型 | 主要职责 | 使用方式 |
|---|---|---|
| 工程知识 | 提供工程理论、参数依据、操作说明 | RAG 检索 |
| 工程规则 | 提供方法选择条件、适用范围和判断约束 | 规则检索与校验 |
| Prompt | 定义 Agent 角色、行为和专业任务流程 | 初始化时组合 |
| 计算工具 | 执行公式计算、参数推荐和确定性操作 | 工具调用 |

四种能力各自独立管理，不应将计算算法直接写入 Prompt，也不应将所有工程规则仅仅作为普通文档处理。

## 二、目录级能力仓库

### 2.1 仓库归属

能力仓库通过 category_id 与零件目录关联。

例如：

文丘里管目录拥有自己的专业能力仓库。

其中可以包含：

- 文丘里结构及流动特征知识。
- 边界层方法选择规则。
- Uniform 首层高度计算工具。
- Smooth Transition 层数推荐工具。
- 文丘里工程辅助 Agent 专属 Prompt。

### 2.2 仓库与模板的关系

同一目录下的模板默认共享专业能力。

例如：

文丘里模板 A 和文丘里模板 B 可以同时使用同一个边界层计算工具。

但：

- A 的聊天记录不能被 B 读取。
- A 的工程参数工作区不能被 B 读取。
- A 的计算结果不能自动进入 B 的会话。
- A、B 可以分别保存自己的工具调用记录。

共享的是专业能力，不是 Agent 的运行状态。

### 2.3 建议的逻辑结构

```text
categories/
  category_venturi/
    manifest.json

    knowledge/
      documents/
      indexes/

    rules/
      boundary_layer_rules.json

    prompts/
      engineer_base.md
      venturi_specialist.md

    tool_bindings/
      allowed_tools.json

templates/
  template_A/
    agent_config.json
    sessions/

  template_B/
    agent_config.json
    sessions/

tool_registry/
  boundary_layer/
    uniform_first_height/
    smooth_transition_layers/
```

这是逻辑结构示意，不要求物理文件全部按照该方式存储。

正式存储方式需结合现有数据库、文件管理和 Agno 持久化机制确定。

## 三、专业知识库

### 3.1 管理目标

知识库用于保存 Agent 进行工程分析时可以检索的专业资料。

资料可以包括：

- PDF、DOCX、MD 等工程文档。
- 工程规范及参考资料。
- 已整理的算法说明。
- 公式推导与适用范围。
- 操作手册。
- 经过整理的历史工程案例。

知识库的作用是为 Agent 提供可检索、可引用的依据。

它不直接执行计算。

### 3.2 文档处理流程

建议采用以下处理过程：

1. 获取原始文档。
2. 提取文本和必要的结构信息。
3. 识别标题、章节和内容层级。
4. 按合理粒度进行文本分块。
5. 生成检索索引。
6. 保存原始文档与索引之间的关联。
7. 提供检索与来源引用。

PDF 中的公式、表格和图片需要根据文档内容选择合适的解析方式。

不能假设所有 PDF 都能通过简单文本提取完整还原。

### 3.3 知识资源数据契约

建议定义 KnowledgeResource：

| 字段 | 用途 |
|---|---|
| resource_id | 资源唯一标识 |
| category_id | 所属目录 |
| title | 文档名称 |
| resource_type | 文档类型 |
| source_ref | 原始文件位置 |
| version | 文档版本 |
| index_status | 索引状态 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

文档分块另外保存：

- chunk_id
- resource_id
- section_path
- content
- embedding_ref
- page_number

原始文档和检索索引需要保持关联。

### 3.4 检索流程

用户提出工程问题时：

1. Agent 判断问题涉及的专业领域。
2. 根据所属目录确定检索范围。
3. 使用关键词或语义检索寻找相关资料。
4. 返回相关内容及来源。
5. Agent 结合用户当前工况进行解释。
6. 重要工程结论展示引用来源。

建议优先评估混合检索，即关键词检索与向量语义检索结合。

具体采用哪种向量数据库、Embedding 模型及检索策略，留待技术整合阶段决定。

### 3.5 检索边界

知识库检索不等于工具调用。

例如：

用户询问“为什么文丘里管需要考虑喉部边界层？”

Agent 可以通过检索工程资料回答。

用户要求“根据喉部直径和流速计算 First Height”，则需要进一步调用对应的计算工具。

Agent 不应将检索到的公式直接当作已经完成的计算结果。

### 3.6 检索结果可信度

建议记录：

- 原始文档名称。
- 文档版本。
- 章节或页码。
- 相关内容。
- 检索匹配信息。

对于不同文档存在冲突的情况，Agent 应指出资料之间的差异，并请求进一步核实。

知识文档中的内容属于参考资料，不应自动成为系统权限或工具调用指令。

## 四、工程规则库

### 4.1 管理目标

工程规则用于保存专业判断逻辑。

例如：

- 哪些工况适合使用某种边界层方法。
- 什么情况下必须询问局部口径。
- 哪些公式只适用于特定流动范围。
- 哪些参数需要用户确认。
- 哪些情况需要提示工程风险。

### 4.2 规则数据结构

建议定义 EngineeringRule：

| 字段 | 用途 |
|---|---|
| rule_id | 规则唯一标识 |
| category_id | 所属目录 |
| rule_name | 规则名称 |
| scope | 适用对象或区域 |
| conditions | 触发条件 |
| description | 规则说明 |
| rationale | 工程依据 |
| source_ref | 依据来源 |
| priority | 规则优先级 |
| version | 规则版本 |
| status | 是否有效 |

### 4.3 规则类型

第一版建议区分：

**判断规则**

帮助 Agent 判断方法的适用性。

**数据完整性规则**

判断某个计算是否缺少必要输入。

**工程约束规则**

明确某些参数的适用范围、限制条件和风险。

**结果解释规则**

规定计算结果需要如何解释，以及必须提示哪些验证事项。

### 4.4 规则执行方式

V1 优先使用结构化规则配置与自然语言解释相结合的方式。

对需要严格执行的数值范围、必填条件和权限限制，由后端进行确定性校验。

Agent 可以使用规则进行工程分析，但不能自行绕过后端校验。

## 五、Prompt 管理

### 5.1 管理目标

Prompt 负责定义不同层级的 Agent 行为。

建议区分：

1. 平台基础 Prompt：通用工程师身份和行为边界。
2. 目录专业 Prompt：文丘里管等专业领域的知识使用方式。
3. 模板专属 Prompt：当前模板需要遵循的特殊工作要求。

### 5.2 Prompt 组合

建议采用明确的组合顺序：

平台基础指令 → 目录专业指令 → 模板专属指令。

不同层级的指令应明确权限和优先级。

如果发生冲突，以平台安全和能力边界为最高约束。

V1 可以只配置平台级和文丘里目录级 Prompt，模板专属 Prompt 暂时保持简单。

### 5.3 Prompt 数据结构

建议包含：

- prompt_id
- category_id
- template_id（可选）
- prompt_type
- content
- version
- priority
- status

Prompt 更新后，后续新一轮 Agent 请求使用更新版本。

已经运行的请求继续使用启动时确定的 Prompt 快照。

## 六、工具库与工具注册

### 6.1 工具库职责

工具库保存已经注册、通过校验且可以被 Agent 调用的确定性工具。

工具可以是：

- Python 计算函数。
- 数值分析工具。
- 工程参数转换工具。
- 已封装的业务服务。

V1 不允许工程辅助 Agent 自行创建或注册新工具。

### 6.2 工具与目录的关系

工具可以由平台统一注册，再授权给一个或多个零件目录使用。

不需要将相同的 Python 源代码复制到每个目录。

目录维护的是工具授权清单。

例如：

文丘里管目录可以使用：

- `boundary_layer.uniform_first_height`
- `boundary_layer.smooth_transition_layers`

其他目录只有在得到授权后才能调用。

### 6.3 工具注册数据契约

建议定义 RegisteredTool：

| 字段 | 用途 |
|---|---|
| tool_id | 工具唯一标识 |
| tool_name | 展示名称 |
| description | 工具用途 |
| version | 工具版本 |
| input_schema | 输入参数定义 |
| output_schema | 输出参数定义 |
| unit_spec | 单位约定 |
| preconditions | 执行前置条件 |
| timeout | 超时限制 |
| permissions | 工具权限 |
| implementation_ref | 实际实现位置 |
| test_status | 测试状态 |
| status | 注册状态 |

### 6.4 输入 Schema 优先

所有工具必须先定义输入输出 Schema，再开发 Agent 调用逻辑。

例如 Uniform First Height 工具：

输入应包括：

- 流体密度。
- 动力黏度。
- 特征速度。
- 有效特征直径。
- 目标第一层 y+。
- 目标壁面区域。

输出应包括：

- 雷诺数。
- 摩擦系数。
- 摩擦速度。
- 第一层中心距离估算值。
- 第一层完整厚度估算值。
- 计算假设与适用范围。

具体字段沿用 02-B 中已经设计的参数定义，并在统一技术整合时核对单位和公式。

### 6.5 工具执行流程

1. Agent 根据用户意图选择已授权工具。
2. 后端检查工具是否存在。
3. 检查当前模板是否有调用权限。
4. 根据 input_schema 校验输入。
5. 执行对应的预注册函数。
6. 校验工具返回结果。
7. 保存调用记录。
8. 将结构化结果交给 Agent 解释。

工具调用失败时，应返回明确的错误类型及必要信息。

Agent 不得伪造计算成功结果。

### 6.6 工具调用安全

工具只能通过受控的注册入口执行。

不允许 Agent 根据用户消息自行构造 Python 文件并执行。

不允许 Agent 任意导入模块、执行系统命令或访问未授权文件。

工具执行应具备超时、异常捕获和必要的资源限制。

## 七、目录能力授权机制

### 7.1 CapabilityBinding

建议通过统一授权关系管理目录可使用的能力。

关键字段：

- binding_id
- category_id
- resource_id
- resource_type
- enabled
- version_constraint

工具、知识和规则均通过明确的授权关系进入目录能力清单。

### 7.2 能力加载

模板 Agent 初始化或发起新一轮请求时：

1. 查询所属目录。
2. 获取目录有效能力清单。
3. 加载平台基础 Prompt。
4. 加载目录专业 Prompt。
5. 获取可用知识检索范围。
6. 获取已授权工具清单。
7. 形成当前 Agent 的有效能力配置。

Agent 不能通过改变 template_id 或自行指定 tool_id 绕过目录授权。

### 7.3 能力更新

目录新增知识、规则或工具后：

- 所属模板 Agent 后续请求可以使用新版本。
- 不修改各模板历史聊天记录。
- 不修改已保存的历史计算结果。
- 正在执行的请求继续使用启动时的能力快照。

## 八、工具和能力的版本管理

建议统一采用版本管理机制。

### 知识文档

文档更新时产生新的资源版本，历史引用仍保留。

### 工程规则

修改规则时产生新版本，记录修改时间和依据。

### Prompt

修改 Prompt 时保留旧版本，方便追溯历史 Agent 行为。

### 计算工具

每次正式更新工具实现时产生新版本。

历史工具调用记录必须能够查到实际使用的版本。

工具停用后，禁止新的调用，但保留历史记录。

对于存在兼容性要求的模板，更新能力时需要执行兼容性检查。

## 九、Agent Runtime 的统一调用流程

用户发起一轮对话时：

1. 根据 template_id 确定 Agent 身份。
2. 获取全局当前模型配置。
3. 获取所属目录的能力清单。
4. 获取当前会话的工程参数工作区。
5. 根据用户意图判断是否需要知识检索。
6. 根据需要加载相关工程规则。
7. 如需计算，检查工具权限及输入 Schema。
8. 执行已注册工具。
9. 将检索资料和工具结果交给模型组织回答。
10. 保存消息、资源引用、工具调用记录和本轮配置版本。

以上能力应通过统一服务组合，不要求每个模板单独实现一套运行程序。

## 十、V1 与未来拓展台的职责划分

### V1

V1 不开发完整的拓展台管理功能。

当前专业能力由开发阶段准备和配置：

- 导入文丘里工程资料。
- 整理边界层工程规则。
- 配置专业 Prompt。
- 注册已有 Python 计算工具。
- 配置目录授权。

通过受控的初始化配置或后端导入流程，使文丘里模板 Agent 能够使用这些能力。

通用零件目录默认没有专业知识和专业计算工具，保留通用工程师对话及联网搜索能力。

### 未来拓展台

未来由拓展台提供可视化能力管理：

- 上传和整理知识。
- 编辑工程规则。
- 创建和优化 Prompt。
- 查看、配置和授权工具。
- 使用拓展台 Agent 辅助创建工具。
- 生成工具代码与测试用例。
- 在隔离环境验证。
- 经用户确认后，由受控服务注册。

未来工具创建流程采用已经确认的方案 B。

拓展台 Agent 的代码生成权限不能传递给模板工程辅助 Agent。

## 十一、异常处理

至少覆盖：

- 文档解析失败。
- 知识索引失败。
- 检索无结果。
- 多份工程资料相互冲突。
- 规则不适用。
- Prompt 组合冲突。
- 工具未注册。
- 工具未授权。
- 输入 Schema 不匹配。
- 工具执行超时。
- 工具返回数据不符合 Schema。
- 能力更新过程中发生版本变化。
- 工具已经停用但历史记录仍需要查看。

所有错误都应保留必要的诊断信息。

---

## 十二、V1 验收标准

1. 每个零件目录拥有独立的能力空间。
2. 同目录模板 Agent 能共享已授权专业知识。
3. 不同模板之间的会话和工程参数相互隔离。
4. Agent 能检索专业知识并提供来源。
5. Agent 能根据工程规则辅助判断。
6. Agent 只能调用已注册且获得授权的工具。
7. 工具输入输出遵循统一 Schema。
8. 工具调用能够保存版本、输入和输出。
9. 目录能力更新不破坏历史结果。
10. 没有专业能力的目录仍能正常使用通用 Agent。
11. V1 不提供 Agent 动态生成和注册工具的能力。
12. 未来拓展台能够复用当前能力仓库及工具注册服务。

**文档状态：V0.1，待需求确认及跨模块技术整合。**

V1 采用开发配置导入模式：
- Codex 通过初始化配置、脚本和后端服务导入专业知识、规则及 Prompt。
- 注册已有 Python 计算工具。
- 将能力授权给对应零件目录。
- 不开发知识管理界面和工具管理界面。
- 未来由拓展台接管这些管理工作。
