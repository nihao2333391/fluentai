# Fluent AI｜02-A 模型配置、Agent 会话与状态恢复

**文档版本：V0.2**

**所属模块：02 工程辅助 Agent 与能力库**

**需求状态：全局统一模型已确认；会话及恢复机制为建议规格，待进一步对齐**

---

## 一、已确认的模型使用原则

系统采用全局统一模型机制。

所有模板的工程辅助 Agent 使用同一个当前生效的模型配置。

不同模板可以拥有不同的专业知识、Prompt、工具权限与对话历史，但不能在模板内部选择独立模型。

### 1.1 模型切换规则

1. 全局模型切换入口统一位于系统设置。
2. 切换成功后，所有模板的后续 Agent 请求使用新模型。
3. 已开始执行的请求继续使用启动时确定的模型。
4. 模型切换不删除或重置已有会话。
5. 模型切换不改变目录级专业能力和工具授权。

建议允许保存多个模型配置，但任意时刻只有一个全局生效配置。

例如保存 DeepSeek、OpenAI 兼容接口等不同配置时，用户可以在设置中选择当前模型，但不需要为每个模板单独设置。

## 二、模型配置的数据契约

### 2.1 ModelConnection

负责描述模型服务连接。

| 字段 | 用途 |
|---|---|
| connection_id | 唯一连接标识 |
| provider | 提供商 |
| adapter_type | Agno 模型适配器 |
| base_url | 服务接口地址 |
| credential_ref | API Key 的安全存储引用 |
| status | 连接配置状态 |

### 2.2 ModelProfile

描述一个可以被全局选择的模型配置。

| 字段 | 用途 |
|---|---|
| profile_id | 唯一模型配置 ID |
| connection_id | 关联连接 |
| display_name | 用户可见名称 |
| model_id | 实际模型标识 |
| generation_config | Temperature 等生成参数 |
| capabilities | 已验证的功能支持情况 |
| revision | 配置版本 |
| enabled | 是否允许选择 |

### 2.3 GlobalModelSettings

管理全局模型选择。

核心字段：

- active_model_profile_id
- settings_revision
- updated_at

系统通过 active_model_profile_id 确定当前有效模型。

**V1 不需要 AgentModelBinding 数据对象。**

所有工程辅助 Agent 在发起新一轮请求时，从全局模型配置服务获得有效模型。

## 三、模板与 Agent 的身份关系

### 3.1 一个模板对应一个独立 Agent 身份

例如：

文丘里模板 A → Agent A → 会话 A

文丘里模板 B → Agent B → 会话 B

两个 Agent 可以使用同一个模型服务，但不能共享会话内容。

### 3.2 Agent 与模型之间的关系

Agent 身份是长期保存的业务对象。

模型实例是执行对话时所需的运行资源。

因此，切换模型不需要删除 Agent 或重新创建模板。

后端可以通过统一 Agent Runtime 动态创建或复用适当的模型适配器，而无需为每个模板长期运行一个独立服务进程。

### 3.3 V1 会话数量

第一版建议每个模板默认只有一个主会话。

后续如果需要多个话题分支，可以扩展会话列表，但不作为当前必需功能。

## 四、Agent 首次初始化

### 4.1 创建模板时

系统创建模板草稿，并建立：

- template_id
- agent_id
- 默认 session_id
- 首次欢迎状态
- 模板与目录能力关联

这一步无需实际请求 AI 模型。

### 4.2 首次进入编辑页面时

前端查询当前模板的 Agent 状态。

若尚未展示欢迎引导，则显示与当前目录能力相匹配的欢迎内容及快捷问题。

文丘里专业 Agent 可以提供 Uniform / Smooth Transition 的引导选项。

未配置专业能力的目录使用通用工程师欢迎内容。

欢迎内容优先由预置配置提供，避免用户每次进入都消耗模型 Token。

### 4.3 再次进入时

恢复已有会话与消息记录。

不会重复创建 Agent，也不会反复显示首次欢迎信息。

首次欢迎状态由后端持久化，避免刷新或多窗口打开时重复初始化。

## 五、Agent 会话持久化

### 5.1 需要保存的数据

| 数据 | 作用 |
|---|---|
| template_id | 确定所属模板 |
| agent_id | 确定 Agent 身份 |
| session_id | 确定对话线程 |
| run_id | 确定某一次执行 |
| message_id | 标识消息 |
| role / content | 保存消息来源与内容 |
| run_status | 保存当前执行状态 |
| model_profile_id / revision | 记录实际使用的模型版本 |
| tool_call_records | 保存工具输入输出及执行结果 |
| created_at / updated_at | 时间信息 |

具体会话与运行记录优先复用 Agno 的持久化能力。业务数据库只增加必要的模板归属关系、欢迎状态和业务索引。

### 5.2 历史保存与模型上下文的区别

系统保留完整的历史消息，但不要求每次都把全部历史发送给模型。

例如，一个会话积累了 100 轮消息，数据库仍保存完整记录；实际模型请求可以根据上下文容量和历史摘要策略选择相关内容。

关键工程参数、用户确认的条件以及工具计算结果必须能够追溯。

### 5.3 会话隔离

后端应检查当前模板与会话的归属关系。

即使前端传入另一个模板的 session_id，也不能加载或修改不属于当前模板的会话。

## 六、对话运行状态

建议每轮 Agent 请求具有独立的执行状态。

| 状态 | 含义 | 用户界面 |
|---|---|---|
| queued | 请求已接收，等待执行 | 排队中 |
| running | 模型正在生成内容 | 正在回复 |
| tool_running | 正在执行专业工具 | 显示工具名称及执行状态 |
| completed | 本轮正常结束 | 展示完整回复 |
| failed | 本轮执行失败 | 显示错误与重试入口 |
| cancel_requested | 用户请求停止 | 正在停止 |
| cancelled | 已确认停止 | 显示已停止 |
| interrupted | 运行被意外中断 | 显示中断与重新生成入口 |

其中 tool_running 可以作为业务展示子状态，由实际工具调用事件驱动。

状态不能仅依靠前端是否还在显示“正在生成”来判断，必须以运行服务的反馈为准。

### 6.1 发送消息

用户发送消息后：

1. 前端提交消息和所属模板 ID。
2. 后端校验模板及会话归属。
3. 检查当前是否存在未结束的运行。
4. 解析全局有效模型及目录能力。
5. 创建 run_id。
6. 保存本轮模型与能力配置快照。
7. 开始模型执行并发送流式事件。
8. 保存最终状态与结果。

第一版建议同一个会话一次只允许执行一轮请求，避免连续发送导致历史顺序错乱。

不同模板的会话可以分别管理，实际并发受模型服务限流和后端资源约束。

### 6.2 显示工具调用

当 Agent 调用已有的边界层计算工具时，前端展示：

- 使用了什么工具。
- 是否正在运行。
- 调用是否成功。
- 关键输入、计算输出及单位。
- 工具版本与必要的计算依据。

面向用户展示可核查的工程分析过程，而不是模型内部的隐藏推理内容。

## 七、页面切换与状态恢复

### 7.1 正常离开页面

用户从模板 A 切换到模板 B。

系统保存模板 A 已经产生的消息、计算记录和运行状态。

再次进入模板 A 时：

1. 加载已有会话。
2. 获取最近一次运行状态。
3. 还原消息和工具结果。
4. 根据运行是否结束，决定是否继续显示生成状态。

### 7.2 正在生成时离开页面

建议 V1 的目标是：

**用户切换前端页面，不自动取消已经交给后端执行的 Agent 请求。**

后端继续处理，用户再次打开时查询对应 run_id。

若运行已经结束，显示完整结果。

若仍在进行，恢复状态，并在技术支持的情况下重新订阅流式输出。

如果现有后端尚不支持脱离前端连接的运行，需要在代码审查阶段确定改造范围。

### 7.3 刷新页面

刷新后重新查询数据库与运行服务。

不能只根据浏览器缓存判断本轮是否完成。

对于已经生成的部分文字，如果服务端没有持久化完整流式事件，可以恢复最近一次可靠保存的结果，并标记不完整的运行状态。

### 7.4 关闭软件并重新打开

应区分两种情况：

**已完成的对话：** 从数据库恢复完整记录。

**软件关闭时仍在运行的对话：** 先检查后端运行是否存活。

如果后端已经停止，标记原运行中断，并提供重新生成入口。

V1 不承诺关闭软件后模型请求仍可继续执行。

### 7.5 中断与重试

用户主动点击停止生成时，后端请求取消对应 run_id，并以最终状态确认取消结果。

重试必须与原始运行记录区分，避免重复写入同一条结果。

已经成功执行的工程工具应保留调用记录，不能因为重新生成文字，就自动重复执行具有副作用的操作。

## 八、全局模型切换的具体行为

### 8.1 正常切换

例如当前所有 Agent 使用模型 A，用户在设置中切换为模型 B。

系统保存新的全局模型配置。

模板 A、B、C 后续发送的消息均使用模型 B。

历史记录继续保留，不迁移、不清空、不重新计算。

### 8.2 存在正在运行的请求

模型切换发生时：

- 已启动的 run 继续使用原模型配置。
- 新创建的 run 使用更新后的模型配置。
- 运行记录保存实际使用的模型 ID 与配置版本。

新旧模型可能同时出现在不同历史消息的元数据中，这是正常现象。

### 8.3 新模型不支持现有功能

如果新模型不支持工具调用，而文丘里 Agent 需要调用计算工具：

系统应明确提示对应能力暂时不可用。

用户仍可以在模型支持的范围内进行普通对话。

不能在工具实际未执行时，声称已经完成工程计算。

### 8.4 新模型连接失败

保留历史记录及 Agent 配置。

发送消息时显示明确错误，并允许用户修改模型配置后重试。

不自动静默切换到其他模型，除非未来单独设计并启用模型故障转移机制。

## 九、前端需要展示的状态

### 9.1 Agent 面板

建议包含：

- 当前全局模型名称。
- 模型配置状态。
- 历史消息。
- 输入区域。
- 发送与停止操作。
- 工具调用状态。
- 运行失败与恢复提示。
- 当前 Agent 能力查看入口。

模型名称为只读展示，不提供模板专属模型选择器。

可以保留跳转到全局模型设置的快捷入口。

### 9.2 未配置模型

仍可编辑 Fluent 模板和查看历史消息。

Agent 输入区域显示“请先配置 AI 模型”，并提供设置入口。

### 9.3 当前模型已变更

对于已打开的 Agent 页面，应同步更新当前模型名称。

必要时提示：

“全局模型已更新，后续对话将使用新模型。”

该提示不要求删除旧消息或重新初始化 Agent。

## 十、后端接口建议

以下是逻辑接口，正式路径需要结合现有 FastAPI 结构确定。

| 操作 | 建议接口 |
|---|---|
| 查看全局模型 | GET /api/ai/models/active |
| 切换全局模型 | PUT /api/ai/models/active |
| 获取模板 Agent | GET /api/templates/{id}/agent |
| 获取会话历史 | GET /api/agent/sessions/{id} |
| 发送消息 | POST /api/agent/sessions/{id}/runs |
| 查询运行状态 | GET /api/agent/runs/{run_id} |
| 取消运行 | POST /api/agent/runs/{run_id}/cancel |

流式响应可优先评估 SSE；如果现有平台已经拥有成熟的 WebSocket 通信机制，也可以复用。

所有写入操作需要定义重复请求处理规则，避免前端重试导致重复生成。

## 十一、测试与验收

至少验证以下场景：

1. 两个模板使用同一模型，但聊天内容相互隔离。
2. 模板退出后再次进入，恢复原会话。
3. 同时打开两个不同模板，不混淆运行结果。
4. 切换全局模型后，新请求使用新模型。
5. 模型切换过程中，已有运行仍使用旧模型。
6. 模型配置失效时，历史聊天仍可查看。
7. 模板页面刷新后，运行状态与后端一致。
8. 前端离开页面后，后端运行按设计继续或明确报告中断。
9. 软件重新打开后，已完成记录能够恢复。
10. 中断运行可以识别并安全重试。
11. 计算工具调用记录保留输入、输出、版本及状态。
12. 未启用的工具不能被 Agent 调用。
