**文档版本：V0.1**

## 一、文档目标

本文件不单独描述一个功能模块，而是规范各模块之间的数据关系、业务流程、技术边界和开发顺序。

目标是让 Codex 在阅读完整需求后，能够理解：

1. 整个平台的使用流程。
2. 每个模块的职责。
3. 哪些模块需要相互通信。
4. 哪些数据结构必须统一。
5. 哪些技术能力需要复用。
6. 哪些事项必须先经过代码审查。
7. 应按照什么顺序完成开发和测试。

### 1.1 开发范围

V1 包括：

- 模板库与零件目录。
- 模板草稿、编辑与发布。
- 工程辅助 Agent。
- 全局 AI 模型配置。
- Agent 会话及工程参数工作区。
- 专业知识、规则、Prompt 和已有工具的接入。
- 任务进程及 Fluent 工作流操作提醒。
- 我的模型与任务的资源引用。
- 拓展台占位页面。

未来拓展台的完整能力管理、工具自动生成与审核发布不属于 V1 开发范围。

## 二、系统总体业务链路

用户从模板库开始创建零件目录。

目录创建成功后，后端初始化该类别的共享能力仓库。

用户在目录内创建模板草稿，系统建立模板关联的 Agent 身份与会话。

用户可以正常编辑 Fluent 工作流参数，也可以向右侧 Agent 提问。

Agent 根据已有知识和计算工具提供工程建议，用户手动填写相应设置。

模板校验通过后发布。

用户从原始模型仓库选择模型，将模板应用到模型，创建独立 Fluent 工作流任务。

任务进程持续展示工作流阶段，并在下一步操作就绪时提醒用户。

生成的网格文件及日志与任务关联，原始模型和模板保持独立。

### 2.1 关键业务关系

```text
零件目录
  │
  ├── 共享专业能力
  │     ├── 工程知识
  │     ├── 工程规则
  │     ├── Prompt
  │     └── 已授权计算工具
  │
  └── 多个模板
        │
        ├── Fluent 工作流配置
        ├── 独立工程辅助 Agent
        │     ├── Agent 会话
        │     ├── 工程参数工作区
        │     └── 工程推荐记录
        │
        └── 发布版本
              │
              ├── 选择原始模型 A
              │     └── 创建任务 001
              │
              └── 选择原始模型 B
                    └── 创建任务 002
```

一个原始模型也允许被多个模板重复应用。

共享能力、模板配置、原始模型和具体执行任务分别管理。

## 三、必须先定义的数据契约

这是项目最重要的技术规范。

### 3.1 三类 Schema

整个系统优先设计三类核心数据契约。

**第一类：业务实体 Schema**

定义零件目录、模板、模型、任务、Agent 会话等对象及其关系。

**第二类：工程参数 Schema**

定义 Fluent 参数、工程输入、物理单位、方法适用范围以及校验规则。

**第三类：工具输入输出 Schema**

定义 Agent 计算工具需要什么信息、如何验证、返回什么结果，以及如何映射到 Fluent 参数。

三类 Schema 应有明确的关联关系。

### 3.2 业务实体统一表

| 业务实体 | 稳定标识 | 主管模块 |
|---|---|---|
| 零件目录 | category_id | 模板库 |
| 模板 | template_id | 模板库 |
| 模板版本 | revision_id | 模板库 |
| 工程辅助 Agent | agent_id | Agent 服务 |
| Agent 会话 | session_id | Agent 服务 |
| AI 模型配置 | model_profile_id | 全局模型配置服务 |
| 工程分析案例 | case_id | Agent 工程参数服务 |
| 工程推荐结果 | recommendation_id | Agent 工程参数服务 |
| 原始模型 | model_id | 我的模型 |
| Fluent 任务 | task_id | 任务服务 |
| 工程能力资源 | resource_id | 能力仓库 |
| 注册工具 | tool_id + version | 工具注册服务 |

同一对象在不同模块中通过稳定标识引用。

数据库表名、目录名及具体实现方式需要结合已有代码决定。

## 四、Fluent 参数 Schema：最高优先级

### 4.1 统一参数定义

必须先对现有 Fluent Meshing 工作流做参数调查。

每个参数应建立统一定义，至少包含：

| 字段 | 作用 |
|---|---|
| parameter_id | 平台内部稳定参数标识 |
| workflow_step_id | 所属 Fluent 工作流步骤 |
| fluent_field | 实际 Fluent 接口参数映射 |
| display_name | 前端展示名称 |
| data_type | 数值、枚举、布尔值等 |
| canonical_unit | 计算和存储使用的标准单位 |
| display_unit | 界面展示单位 |
| default_value | 默认值及来源 |
| applicable_methods | 哪些网格方法适用 |
| validation_rules | 范围、必填及关联校验 |
| schema_version | 参数定义版本 |

需要区分平台内部字段名称、前端展示名称与 Fluent/PyFluent 的真实参数名称。

三者可以不同，但必须有明确映射。

### 4.2 参数表是共同的数据依据

同一参数定义供以下功能使用：

- 模板编辑页面：展示与校验设置。
- 工程辅助 Agent：理解参数含义。
- 专业计算工具：校验计算输入和输出。
- 参数推荐卡片：生成用户可填写的建议。
- Fluent 执行服务：转换并应用实际设置。

如果现有代码已经具有成熟的参数元数据或映射机制，应优先复用，而不是另起一套相互独立的参数配置系统。

### 4.3 不同方法的参数差异

以边界层设置为例：

Uniform 和 Smooth Transition 存在不同的参数适用关系。

因此参数 Schema 不仅需要记录字段，还应记录字段的适用方法及关联条件。

例如 First Height 的推荐结果主要对应 Uniform 分支。

Smooth Transition 的层数推荐则与其自己的参数设置及计算假设相关。

具体参数的实际可编辑性、默认值、单位和 Fluent 字段名称，需要结合 Fluent 2025 R2 及现有工作流代码核实。

### 4.4 单位统一

建议数值计算统一使用 SI 单位。

前端允许按照 Fluent 页面及用户习惯显示 mm、m/s 等单位。

参数输入、后端计算、推荐结果及 Fluent 调用之间需要明确单位转换。

不得在不同模块中对同一字段隐式使用不同单位。

## 五、工程参数与 Fluent 参数的区别

这两类参数相关，但不能合并成同一个对象。

### 5.1 工程输入参数

例如：

- 喉部直径。
- 入口速度。
- 流体密度。
- 动力黏度。
- 目标 y+。

它们是 Agent 分析和计算工具的输入。

### 5.2 Fluent 设置参数

例如：

- Offset Method。
- Number of Layers。
- Growth Rate。
- First Height。
- Transition Ratio。

它们是用户在 Fluent 工作流中实际填写的设置。

### 5.3 二者之间的转换链路

```text
用户提供工程信息
        ↓
工程参数工作区
        ↓
输入 Schema 校验
        ↓
计算工具
        ↓
计算输出 Schema
        ↓
工程推荐结果
        ↓
Fluent 参数映射
        ↓
前端推荐卡片
        ↓
用户手动填写模板
```

Agent 不直接将自然语言内容写入 Fluent 工作流。

每一次计算保留输入快照，保证结果能够追溯。

## 六、跨模块职责及接口关系

### 6.1 模板库与能力仓库

创建零件目录时，由模板库服务创建目录记录。

能力仓库服务负责为其初始化共享能力空间。

专业能力尚未配置时，目录仍然可以使用默认通用 Agent。

模板库不直接操作专业工具的执行代码。

### 6.2 模板库与 Agent 服务

创建模板草稿时，建立独立 Agent 身份和会话关联。

Agent Runtime 统一运行，不为每个模板建立独立常驻服务进程。

模板中的 Fluent 参数由模板服务管理。

Agent 会话和工程推荐结果由 Agent 服务管理。

### 6.3 Agent 与能力仓库

Agent 根据所属目录获取专业知识、规则、Prompt 和已授权工具。

工程辅助 Agent 只消费已配置能力。

能力仓库的修改与发布由独立管理流程负责。

V1 专业能力通过开发配置导入，不需要拓展台管理界面。

### 6.4 Agent 与模板参数

Agent 可以输出 Fluent 参数建议。

V1 采用人工填写方式。

Agent 不直接修改模板表单、模板数据或 Fluent 工作流。

工程参数工作区中的数据更新，也不等于 Fluent 设置参数发生修改。

### 6.5 模板库与任务进程

应用模板时创建独立任务。

任务保存本次实际使用的模板版本与配置快照。

后续修改模板，不改变已有任务的配置。

### 6.6 我的模型与任务进程

我的模型提供原始模型文件。

任务引用模型，但在独立空间保存网格生成结果和日志。

同一个模型可以被多个任务重复使用。

删除任务不能删除共享原始模型。

## 七、Agent 模型配置及会话规则

### 7.1 全局统一模型

已确认所有工程辅助 Agent 使用同一个当前生效的全局模型。

可以保存多个模型配置，但任意时刻只有一个全局生效配置。

模板不能单独覆盖模型选择。

### 7.2 会话独立

每个模板拥有独立的 Agent 身份和主会话。

模板 Agent 共享当前模型服务和目录专业能力，但各自保存聊天历史、工程输入和计算结果。

### 7.3 切换模型

切换全局模型后：

- 后续新请求使用新模型。
- 已运行的请求继续使用原模型。
- 历史会话和计算结果保持不变。
- 专业工具权限不变。

### 7.4 会话恢复

用户切换模板或重新进入应用时，从后端恢复已保存内容。

已完成的对话、工具记录和工程参数持久化保存。

运行中断与正常结束应当区分，不通过前端显示状态推断执行已经成功。

## 八、任务进程的统一状态机制

任务进程用于提示用户下一步操作是否就绪。

### 8.1 两层状态

**第一层：工作流位置**

表示任务处于面网格或体网格的哪个步骤。

**第二层：操作状态**

表示当前正在处理、等待用户操作、生成中、失败还是已完成。

任务可以使用四个内部里程碑记录详细进展，但用户界面重点突出面网格和体网格两个主要节点。

具体呈现颗粒度在 UI 实现前统一确定。

### 8.2 统一状态来源

任务卡片和实际 Fluent 工作流页面必须依据同一套业务状态判断下一步操作是否可执行。

尤其要复用现有平台控制“生成面网格”按钮显示与启用的业务条件。

应由后端任务服务负责持久化状态和对外提供状态查询。

前端不能仅通过按钮是否出现在 DOM 中判断任务已经就绪。

### 8.3 操作提醒

当下一步操作真正可执行时：

- 更新任务状态。
- 任务卡片突出显示。
- 在任务列表中提高显示优先级。
- 用户点击卡片后返回对应操作页面。

查看任务不自动清除提醒。

只有实际执行对应操作，或者该操作条件失效时，才更新提醒状态。

### 8.4 完成与删除

任务完成后继续保留。

用户手动删除时，默认保留网格文件与日志。

可以额外勾选清理该任务专属文件。

原始模型、模板及其他任务共享资源受到保护。

失败后的重试和恢复策略暂时保持待定，不作为本轮技术设计的确定性要求。

## 九、文件仓库与数据归属

建议遵守以下逻辑归属：

| 数据 | 归属位置 |
|---|---|
| 原始 CAD 模型 | 模型资源仓库 |
| 模板工作流配置 | 模板数据仓库 |
| 专业文档与规则 | 目录能力仓库 |
| 工具程序 | 后端工具注册体系 |
| Agent 聊天记录 | Agent 会话存储 |
| 工程参数与推荐 | Agent 工程数据存储 |
| 生成网格文件 | 任务工作空间 |
| 任务执行日志 | 任务工作空间 |

实际数据库及文件目录结构应结合当前 Electron 和 FastAPI 项目确定。

不要求为了满足逻辑分层而重构整个源代码目录。

## 十、跨模块接口开发规范

每个模块需要对外提供明确的服务接口。

接口规格应包括：

1. 业务目标。
2. 请求方与响应方。
3. 输入 Schema。
4. 输出 Schema。
5. 数据所有权。
6. 权限校验。
7. 状态变化。
8. 错误类型及处理方式。
9. 幂等性与重复请求控制。
10. 关联版本及追溯信息。

### 10.1 重要接口关系

| 发起模块 | 接收模块 | 操作 |
|---|---|---|
| 模板库 | 能力仓库 | 初始化目录能力空间 |
| 模板库 | Agent 服务 | 创建或获取模板 Agent |
| Agent 服务 | 能力仓库 | 获取有效知识及工具 |
| Agent 服务 | 工程参数服务 | 读取、确认、更新输入 |
| Agent 服务 | 工具服务 | 执行已授权计算 |
| 模板库 | 我的模型 | 获取可应用模型 |
| 模板库 | 任务服务 | 创建模板应用任务 |
| Fluent 执行服务 | 任务服务 | 更新工作流状态 |
| 任务进程页面 | 任务服务 | 获取任务状态及操作入口 |

接口的实际 URL、方法及数据结构待 Codex 完成现有代码审查后确定。

## 十一、跨模块一致性检查

全部模块文档完成后，需要集中检查以下问题。

### 11.1 对象一致性

同一对象是否在多份文档中被重复定义？

例如模板 ID、目录 ID、任务 ID 是否一致。

### 11.2 参数一致性

同一 Fluent 参数是否出现多个字段名称、单位或取值含义？

例如 First Height 在计算工具、推荐卡片和实际 Fluent 表单之间是否存在差异。

### 11.3 状态一致性

不同页面是否对同一个任务使用不同的状态判断？

例如工作流按钮已经可以点击，但任务进程仍显示“准备中”。

### 11.4 权限一致性

工程辅助 Agent 是否始终只有对话、检索和已授权工具能力？

未来拓展台 Agent 的代码生成权限是否与它隔离？

### 11.5 版本一致性

历史任务是否固定使用创建时的模板配置？

历史推荐是否能够关联计算时使用的输入和工具版本？

## 十二、交付 Codex 的整体工作要求

所有模块完成详细设计并统一整合后，才向 Codex 提交完整文档集。

### 第一阶段：全局代码审查

Codex 先阅读完整需求。

分析现有 Electron 前端、FastAPI 服务、Fluent 工作流、模板结构、模型管理和数据存储。

输出目前已有能力、可复用代码及需要改造的部分。

本阶段不修改代码。

### 第二阶段：技术方案设计

先完成：

- 统一数据契约。
- Fluent 参数 Schema 对照表。
- 模块服务职责。
- 跨模块接口。
- 状态机及事件流。
- 数据迁移方案。
- 技术框架与依赖选择。
- 开发顺序及风险分析。

### 第三阶段：技术方案确认

由用户审核 Codex 提供的技术方案。

对于与现有业务需求不一致的内容，先修改方案与需求文档，再实施。

### 第四阶段：分模块开发

按照依赖关系分模块实现。

每次修改后执行针对性测试，并维护开发日志。

### 第五阶段：系统集成测试

验证模块间的完整业务链路：

创建目录 → 创建模板 → Agent 辅助 → 保存模板 → 选择模型 → 创建任务 → Fluent 工作流推进 → 任务提醒 → 任务完成。
