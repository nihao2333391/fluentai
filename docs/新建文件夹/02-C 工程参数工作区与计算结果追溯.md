# Fluent AI｜02-C 工程参数工作区与计算结果追溯

**所属模块：02 工程辅助 Agent 与能力库**

**文档版本：V0.1**

**状态：推荐设计方案，待需求确认**

**设计目标：让自然语言对话中的工程信息能够稳定转化为计算工具可使用的结构化数据，并保证参数变化和计算结果可追溯。**

---

## 1. 基本设计原则

工程参数工作区是 Agent 的内部工程数据管理机制。

用户通过文字、图片或附件提供信息。Agent 负责识别信息，系统负责保存、校验、更新和关联。

V1 保留自然语言作为主要交互方式，不要求用户填写完整工程参数表才能使用 Agent。

参数工作区具有以下职责：

1. 保存已识别的工程参数。
2. 区分参数所属模型及几何区域。
3. 记录数据来源、单位和确认状态。
4. 根据工具 Schema 判断缺失参数。
5. 在计算前生成不可变的输入快照。
6. 检测参数修改对已有计算结果的影响。
7. 支持方法分支切换与历史结果对比。

参数工作区独立于 Fluent 模板表单，V1 不自动修改模板参数。

## 2. 参数工作区归属

建议引入 `EngineeringCase`（工程分析案例）。

一个模板 Agent 可以存在不同时间创建的工程分析案例。

例如：

- 案例 A：入口直径 80 mm，喉部直径 45 mm。
- 案例 B：入口直径 80 mm，喉部直径 55 mm。

两个案例不能直接混用几何数据。

### 2.1 数据关联

建议关系：

```text
Template
  └── AgentSession
        └── EngineeringCase
              ├── EngineeringInputs
              ├── InputSnapshots
              └── Recommendations
```

V1 默认每个模板会话创建一个活动案例。

如果用户明确切换到另一份模型，系统应提示创建新案例或更新当前案例，而不是直接覆盖所有原有尺寸。

完整的多案例管理界面可以留待后续实现。

## 3. 工程参数分类

参数工作区使用可扩展的数据结构，而不是为所有零件统一要求固定参数。

当前文丘里案例可配置以下分类：

| 分类 | 示例 |
|---|---|
| 几何结构 | 主入口直径、喉部直径、侧支直径、几何位置 |
| 工况条件 | 主入口速度、侧支入口速度、温度、压力、流量 |
| 流体物性 | 密度、动力黏度及其对应的流体区域 |
| 研究目标 | 温度混合、压力变化、壁面流动特征 |
| 网格目标 | 第一层目标 y+、外层覆盖目标、增长率 |
| 计算假设 | 特征速度取值方式、使用的经验关系、适用范围 |

对于冷热混合文丘里管，需要特别保留主入口与侧支入口之间的区别。

例如主入口速度和侧支入口速度必须使用不同参数标识。

对于特征直径，也要明确是入口直径、喉部直径，还是某区域的水力直径。

## 4. 参数数据契约

建议参数记录至少包含：

| 字段 | 含义 |
|---|---|
| parameter_id | 稳定参数标识 |
| value | 参数数值或文本 |
| canonical_unit | 内部标准单位 |
| display_unit | 用户输入或展示单位 |
| region_id | 对应几何或物理区域 |
| source_type | 数据来源类型 |
| source_ref | 原始消息、图片或其他来源引用 |
| confirmation_status | 参数确认状态 |
| updated_at | 最近修改时间 |
| revision | 参数版本 |

### 4.1 单位管理

内部计算优先使用统一的 SI 单位。

例如用户提供：

喉部直径 = 55 mm

工作区可以保存内部计算值 0.055 m，同时保留原始输入和展示单位。

单位转换由后端确定性规则完成。

### 4.2 数据来源

建议区分：

- 用户直接提供。
- 图片识别提取。
- 已有工程配置引用。
- 公式推导。
- 工程估算。

对于图片识别出的尺寸，如果存在模糊、遮挡或单位不明确，需要向用户确认。

对于需要使用假设值才能完成的计算，必须说明假设，并在计算快照中记录。

### 4.3 参数确认状态

建议使用：

- `proposed`：识别出的候选值，待核实。
- `confirmed`：用户明确提供或确认的有效值。
- `invalid`：未通过参数校验。
- `superseded`：已被新版本替代的旧值。

在对计算结果影响较大的输入存在歧义时，系统应先向用户确认再计算。

## 5. 自然语言更新参数

用户可以通过对话直接修改数据。

例如：

“之前喉部直径填错了，改成 55 mm。”

Agent 应识别：

- 修改对象：当前案例的喉部直径。
- 新数值：55。
- 单位：mm。
- 旧值：45 mm。

随后由后端参数服务执行更新，产生新的参数版本。

Agent 向用户反馈：

“已将当前案例的喉部直径由 45 mm 更新为 55 mm。此前基于 45 mm 计算的 First Height 需要重新计算。”

对于用户表述不明确的情况，例如仅说“直径改成 55”，Agent 需要先确认具体修改的是哪一个口径。

**参数更新应有明确的数据操作机制，而不只是让大模型在下一轮对话中记住一句话。**

V1 可以通过预注册的参数管理服务或受控工具实现这一机制。该工具仅修改 Agent 工程工作区，不修改 Fluent 模板。

## 6. 缺失参数检查

参数是否缺失，由具体分析任务决定。

例如：

**方法选择阶段**

可能需要几何特征、研究目标、工况以及局部网格关注区域。

**Uniform 计算阶段**

需要目标壁面区域、流体物性、特征速度、特征直径、目标第一层 y+ 等。

**Smooth Transition 层数计算阶段**

需要第一层目标 y+、外层覆盖目标 y+、增长率等。

缺失检查使用预注册工具的输入 Schema 和目录专业规则。

Agent 负责以自然语言询问缺失信息。

### 6.1 避免无关参数收集

如果用户只是想了解 Uniform 与 Smooth Transition 的区别，不要求提供完整几何和工况。

只有用户决定进行实际推荐或计算时，才进一步收集必要参数。

### 6.2 信息来源优先级

建议原则：

1. 用户明确纠正的最新有效值。
2. 用户明确提供并确认的当前值。
3. 已核实的已有工程数据。
4. 用户确认后的图片识别结果。
5. 明确标记的工程估算值。

不同来源发生冲突时，不应静默覆盖，而应展示差异并确认。

## 7. 计算快照

每次调用专业计算工具时，系统生成独立的 `InputSnapshot`。

建议包含：

- snapshot_id
- case_id
- input_revision
- tool_id
- tool_version
- inputs
- units
- input_sources
- assumptions
- created_at

快照一旦创建，不再直接修改。

例如：

```json
{
  "snapshot_id": "snapshot_001",
  "case_id": "venturi_case_A",
  "tool_id": "boundary_layer.uniform_first_height",
  "tool_version": "1.0",
  "inputs": {
    "hydraulic_diameter": 0.045,
    "fluid_density": 998.2,
    "dynamic_viscosity": 0.001,
    "target_first_yplus": 1
  },
  "input_sources": {
    "hydraulic_diameter": "confirmed_geometry"
  }
}
```

以上仅为结构示例，省略了其他必需的计算参数，不作为可直接执行的工具输入。

计算工具只接受通过校验且满足完整输入要求的数据。

## 8. 计算结果管理

每份工程推荐结果应关联：

- 计算输入快照。
- 计算工具及版本。
- 计算输出。
- Fluent 参数映射。
- 推荐依据。
- 工程假设。
- 待验证事项。

建议结果具有以下状态：

| 状态 | 含义 |
|---|---|
| current | 基于当前有效参数，结果仍适用 |
| stale | 相关输入已变化，需要重新计算 |
| failed | 本次计算失败 |
| superseded | 已由新的计算结果取代 |

例如，修改喉部直径可能影响特征速度、Re、摩擦速度和 First Height。

系统应根据工具输入依赖关系识别受影响的结果，而不是将所有历史结果统一标记为失效。

## 9. Uniform 与 Smooth Transition 分支管理

同一个工程案例可以分别生成两个方法的推荐结果。

切换分支时，共享已确认的模型几何、工况和研究目标。

各分支独立保存其特有参数、计算快照与推荐结果。

例如：

```text
文丘里案例 A
│
├── 共享工程输入
│   ├── 几何尺寸
│   ├── 物理工况
│   └── 研究目标
│
├── Uniform
│   ├── 目标第一层 y+
│   ├── First Height 计算快照
│   └── 推荐结果
│
└── Smooth Transition
    ├── 第一层与外层目标 y+
    ├── Growth Rate
    ├── Layers 计算快照
    └── 推荐结果
```

这样用户可以比较两条分支，也能追溯各自使用的工程数据。

## 10. 前端工作区展示

建议在 Agent 面板中增加一个可展开的“已识别工程参数”区域。

默认保持折叠，避免占用聊天空间。

展开后可以看到：

- 已识别参数及单位。
- 对应模型或区域。
- 参数来源。
- 是否需要确认。
- 最近更新情况。
- 当前推荐结果是否需要重新计算。

用户仍主要通过对话修改参数。

对于参数确认，可以提供简洁的确认、纠正入口。

V1 不需要将其开发成复杂的工程数据编辑器。

## 11. 数据持久化

工程参数工作区应与 Agent 会话建立稳定关联。

用户关闭模板、切换页面或重新启动应用后，已确认的参数、计算快照和历史推荐应能够恢复。

对话摘要不能替代结构化工程参数。

如果后续模型上下文压缩，系统仍从工程工作区读取真实的当前参数，而不是从摘要中重新猜测数值。

## 12. 与其他模块的边界

**与模板库：**

通过 template_id 建立关联，但不直接修改 Fluent 设置。

**与 Agent 会话：**

通过 session_id 关联对话来源，允许恢复和继续分析。

**与能力仓库：**

根据已授权工具的 Schema 和工程规则，判断所需输入与数据有效性。

**与任务进程：**

V1 不直接产生网格划分任务，也不自动把工程推荐应用到任务配置。

**与我的模型：**

允许引用已有模型资源及相关文件，但不会自动改变原始模型。

## 13. Codex 实施前审查重点

1. Agno 现有会话状态及业务数据存储机制。
2. FastAPI 是否已有可复用的参数校验与单位转换模块。
3. 已有边界层工具的真实输入输出结构。
4. 现有模型资源及面标签的标识方式。
5. 当前图片上传和附件保存机制。
6. 对话中参数更新如何接入受控后端服务。
7. 如何在最小改动下保存参数快照与历史推荐。

在这些内容审查完成前，不固定实际数据库表名和 API 路径。

## 14. V1 验收标准

1. 用户通过聊天提供工程参数，系统可以结构化保存。
2. 图片识别结果能够在计算前接受核实。
3. 参数记录具有单位、来源和区域信息。
4. 工具调用前检查必要输入。
5. 参数修改能够形成新版本。
6. 计算工具获得确定、可校验的输入快照。
7. 修改相关输入后，旧推荐结果能够标记为需要重新计算。
8. Uniform 与 Smooth Transition 的结果独立保存。
9. 页面重新打开后，参数及结果可以恢复。
10. 参数工作区不会直接修改 Fluent 模板表单。

为了降低开发量，也避免 Agent 面板过于拥挤，我建议第一版采用默认折叠的工程参数工作区。
工程辅助 Agent

已从你提供的模型信息中提取部分参数，请核对后继续计算。

已识别工程参数已确认 2 项 · 
待补充 1 项
请问侧支直径是多少？也可以上传包含尺寸的结构图。


这里的参数列表应当是当前分析任务相关的参数，而不是把整个 Fluent 的所有设置都展示出来。
