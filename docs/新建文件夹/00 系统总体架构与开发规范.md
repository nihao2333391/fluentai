# Fluent AI 系统总体架构与开发规范

**文档编号：ARCH-00**  
**当前版本：V0.1**  
**文档性质：系统级需求与技术设计基线**  
**状态：初稿，待现有代码审查及逐模块细化**

---

## 1. 项目定位与改造目标

### 1.1 项目定位

Fluent AI 是基于现有 Electron 桌面应用、FastAPI 后端及 ANSYS Fluent Meshing 工作流构建的网格划分辅助平台。

本次改造以保留现有网格划分自动化能力为基础，增加模板分类管理、工程辅助 Agent、多任务操作提醒和可扩展的专业能力仓库。

### 1.2 V1 模块范围

| 模块 | V1 目标 |
|---|---|
| 模板库 | 零件目录、模板草稿、编辑、发布与应用 |
| 工程辅助 Agent | 通用工程师、联网搜索、专业知识与工具调用 |
| Agent 能力仓库 | 共享知识、规则、Prompt 和预注册工具 |
| 任务进程 | 多任务列表、操作就绪提醒与任务返回 |
| 我的模型 | 保留原始模型资源管理能力 |
| 拓展台 | 仅建立基础页面空壳和导航入口 |

V1 优先完成文丘里管边界层工程辅助案例。其他零件目录在没有专业配置时使用通用工程师 Agent。

## 2. 总体技术架构

### 2.1 推荐技术分层

**第一层：桌面交互层**

以现有 Electron 应用为基础，保留已有前端框架和组件体系。

主要负责页面呈现、表单交互、聊天显示、任务提醒和操作反馈。

**第二层：FastAPI 业务服务层**

作为统一业务入口，负责目录与模板管理、模型资源引用、任务状态、参数校验、能力授权及数据持久化。

**第三层：Agent 运行层**

优先评估 Agno SDK 与现有 FastAPI 的集成。

负责 Agent 初始化、会话管理、上下文组装、知识检索、工具调用及流式响应。

**第四层：Fluent 执行层**

复用已有 Fluent/PyFluent 执行能力，负责网格工作流调用、实际生成操作和执行状态反馈。

**第五层：数据与资源层**

管理模板配置、业务数据库、Agent 会话、工程文档、工具配置、原始模型及任务生成文件。

### 2.2 模块边界原则

1. 模板库负责模板定义，不直接管理 Fluent 运行进程。
2. Agent 负责工程辅助，不直接修改模板设置。
3. 工程辅助 Agent 只能使用已有知识、联网搜索和授权工具，不具备代码生成或动态创建工具能力。
4. 任务服务管理模板应用后的执行状态。
5. 我的模型负责原始模型资源，不承担任务结果归档中心职责。
6. 拓展台未来负责专业能力的建设和管理。
7. 各模块通过稳定的数据模型和服务接口通信。

## 3. 核心开发原则

### 3.1 Schema First：数据契约优先

开发任何使用工程参数的功能之前，先确认其字段结构。

尤其是 Fluent 工作流参数，必须先核对现有参数定义，再设计统一 Schema。

每个参数应明确：

- 稳定字段 ID、Fluent 对应字段及所属工作流步骤。
- 参数类型、单位、默认值及有效范围。
- 不同工作流方法下的适用条件。
- 用户输入、计算工具及 AI 推荐等数据来源。
- 校验规则与错误反馈。
- Schema 版本与兼容要求。

**前端表单、Agent 参数推荐和后端 Fluent 参数转换，应尽可能引用同一套权威字段定义。**

优先复用现有项目的表单元数据和参数映射机制。

### 3.2 现有代码优先

Codex 在修改功能前，必须先定位现有代码中的对应实现。

对于已有组件、接口、参数结构、计算工具和 Fluent 调用逻辑，优先扩展与复用。

新增模块时，应说明为什么现有实现无法满足需求。

### 3.3 成熟框架优先

Agent Runtime 优先评估 Agno。

其他技术组件同样应优先采用成熟、易维护的方案。

每项新增依赖需要说明其解决的问题、与现有架构的兼容性以及维护成本。

### 3.4 单一数据责任源

每类核心业务数据指定主要管理服务。

例如：

- 模板参数由模板服务管理。
- Agent 会话由 Agent 会话服务管理。
- 工具注册由能力服务管理。
- 任务就绪状态由任务服务管理。
- Fluent 实际执行状态由 Fluent 执行服务提供。

多个模块使用相同数据时，通过接口或共享契约访问，减少重复定义和状态冲突。

### 3.5 版本与历史可追溯

模板、专业能力、工具和工程推荐结果应保留必要的版本关联。

模板应用任务使用创建时的配置快照。

已经完成的计算记录保留原始输入、工具版本和输出，后续能力更新不直接覆盖历史结果。

## 4. 核心业务对象与数据关系

| 对象 | 核心关联 | 说明 |
|---|---|---|
| PartCategory | category_id | 零件类别及共享仓库 |
| MeshTemplate | template_id、category_id | 网格划分模板 |
| TemplateRevision | revision_id、template_id | 模板配置版本 |
| TemplateAgent | agent_id、template_id | 模板独立 Agent 身份 |
| AgentSession | session_id、agent_id | 模板专属会话 |
| CapabilityResource | resource_id、category_id | 共享工程知识和规则 |
| RegisteredTool | tool_id、version | 已注册计算工具 |
| GeometryModel | model_id | 导入的原始几何模型 |
| MeshingTask | task_id、revision_id、model_id | 一次具体模板应用任务 |

以上为逻辑对象，数据库表结构需要结合现有实现确定。

### 4.1 模板与 Agent

一个零件目录可以包含多个模板。

每个模板具有独立 Agent 身份、会话与专属配置。

同目录模板默认继承该目录的共享专业能力，同时允许按权限禁用或覆盖部分配置。

### 4.2 模板与执行任务

一个正式模板可以被多次应用。

每次应用生成独立任务，记录目标模型、模板版本和执行状态。

修改模板不会自动修改已经创建的任务。

### 4.3 模型与任务

我的模型保存原始几何资源。

任务引用模型资源，并将生成文件和执行日志保存在任务关联的数据空间中。

## 5. Agent 运行与能力继承规范

### 5.1 默认通用工程师

未配置专业能力时，Agent 默认具备：

- 通用工程问答。
- 联网搜索。
- 自然语言解释与建议。
- 独立会话及历史恢复。

通用 Agent 不拥有专业工具调用、代码生成或修改仓库的权限。

### 5.2 专业能力继承

能力由平台默认配置、目录共享配置以及模板专属配置共同确定。

所有可执行工具均须经过后端注册及授权。

专业知识、规则和工具更新后，模板 Agent 从后续对话开始加载有效版本。

### 5.3 模板 Agent 生命周期

创建模板草稿时，建立 Agent 身份和默认会话关联。

首次进入编辑页面时，展示欢迎介绍与可点击的推荐问题。

重新进入时恢复已有消息，避免重复初始化。

会话记录和工程计算结果持久化保存。

模型上下文容量接近限制时，当前有效回答完成后显示预警；必要时整理模型输入上下文，保留原始历史。

### 5.4 专业案例

V1 使用文丘里边界层工程辅助作为专业能力验证案例。

能力包括 Uniform / Smooth Transition 方法选择、Uniform First Height 计算和 Smooth Transition Layers 推荐。

计算方法优先复用既有《边界层参数封装》研究成果及对应工具脚本。

## 6. 任务状态设计原则

任务进程用于多任务操作提醒，而非传统计算耗时百分比监控。

任务界面使用两个主要里程碑：面网格与体网格。

重点显示任务是否进入下一步可操作状态。

任务主标题为应用的模板名称，副标题为被应用模型文件名称。

有任务时，主页面采用上方模板库 65%、下方任务进程 35% 的布局；任务区域独立滚动。

任务完成后继续保留，由用户手动删除。

删除时默认保留生成文件与日志，用户可选择一并清理，原始模型和模板始终受到保护。

**任务就绪判定应优先复用现有平台控制网格生成按钮的业务状态。**

具体状态来源和多任务持续运行能力，必须先通过代码审查验证。

## 7. 文件仓库与数据存储原则

开发源代码、用户业务数据、工程资源及计算产物应分开管理。

建议逻辑结构：

```text
project/
├── frontend/
├── backend/
│   ├── agent/
│   ├── capabilities/
│   ├── templates/
│   └── meshing/
└── workspace-data/
    ├── categories/
    ├── tasks/
    ├── models/
    └── database/
```

该结构只是职责示意，暂不要求重构现有工程目录。

实际桌面部署中，用户数据应保存于可写位置；大型网格产物可以采用独立可配置的数据目录。

业务数据库优先评估现有存储实现，SQLite 作为本地桌面应用的候选方案之一，尚未最终确定。

## 8. 前后端接口规范

各模块开发前需先定义接口契约，至少包含：

- 请求与响应 Schema。
- 资源 ID 与归属关系。
- 成功及失败状态。
- 数据校验和版本兼容规则。
- 幂等性与重复操作处理。
- 持久化边界。
- 状态变更事件及前端反馈。

对长时间运行的 Fluent 任务，需要明确任务启动、状态查询、结果更新与恢复行为。

对 Agent 流式响应，需要区分普通文字、工具调用事件、错误信息及结构化参数结果。

接口设计完成后，再开发依赖这些接口的前端组件。

## 9. Codex 开发工作规范

每个模块按以下顺序实施：

1. **代码审查**：定位现有功能、数据结构和调用链。
2. **需求对齐**：明确保留、修改和新增内容。
3. **技术设计**：先确定 Schema、接口、状态机及服务职责。
4. **设计确认**：说明关键技术选择、风险和复用方案。
5. **功能开发**：按独立、可验收的功能单元实现。
6. **测试验证**：覆盖正常操作、异常情况、数据持久化和模块隔离。
7. **文档同步**：记录实际修改内容、设计调整、测试结果与遗留问题。

对于缺陷修复，先分析问题现象、相关调用链和根因，再选择修复方案。

每次开发完成后，应提供可读的变更记录，说明修改了哪些文件、实现了什么功能、测试了什么以及尚有哪些限制。

---

## 10. 需求状态管理

后续所有模块规格统一采用三种标记：

**已确认需求**：经过业务讨论确认，可以作为产品要求。

**待技术验证**：业务目标明确，但必须审查现有代码才能确定实现方式。

**待产品决策**：尚未确认的交互、规则或功能范围。

Codex 可以对已确认需求进行实现方案设计，但不应擅自把待产品决策事项当作已经批准的功能。

---

## 11. 当前必须完成的代码审查

正式开发前，优先核查：

1. 现有 Electron 前端框架、路由和状态管理机制。
2. 当前模板编辑器的参数来源、保存结构和工作流映射。
3. FastAPI 已有接口、数据存储及文件管理方式。
4. Fluent/PyFluent 的启动、连接、执行和状态反馈流程。
5. 原有“生成面网格”按钮的显示与启用条件。
6. 模型导入、面标签及模板应用之间的关系。
7. 是否已存在可复用的 Agent、模型配置或工具管理服务。

审查完成后，输出《现有系统代码审查与改造影响分析》，再将结论写入本规范的下一版本。

## 12. V0.1 验收标准

本规范在现阶段的验收目标是：

- 业务模块职责没有重叠或冲突。
- 模板、Agent、能力仓库和任务之间的归属关系明确。
- Fluent 参数映射具有统一的数据契约设计原则。
- 当前 V1 与未来拓展台的范围清晰。
- 不确定的技术实现均有待审查标记。
- 各模块文档可以引用本规范，而不必重复设计相同的基础机制。
